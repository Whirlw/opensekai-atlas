# 0007 时间网格只有一种：一小节 = 1920 tick = 四拍

## 状态

已采纳（2026-11-10）。

## 背景

谱面里的 `ticks` 有两种可能的读法：

1. **时间单位**：480 tick = 一个四分音符，1920 tick = 四拍，和拍号无关
2. **记谱单位**：一小节 = `拍号 × 480` tick，3/4 就是 1440

谱面确实带拍号事件（3/4、6/8 之类），我们为此尝试过第 2 种读法：让 `bar` / `barProgress` 按当前拍号走、让长条内的自动点按该小节拍号切分。

结果：所有 4/4 谱面正常，**所有带流速变化（HighSpeed）的谱面整体错位**，且 3/4 谱的长条内部点被拉成 320 tick 一档（`bar` 仍按 1920 递增，进度却按拍号切分，两者不同步）。

## 决定

引擎只使用第 1 种读法：

- `TICKS_PER_BEAT = 480`、`TICKS_PER_BAR = 1920`，恒为四拍
- `bar` / `barProgress` 永远是「tick ÷ 1920」的小数与整数部分
- 长条内的自动点：**每 240 tick 一个**（八分音），从 tick 常量推出，不读 `timeSignature`
- 谱面的拍号事件照常解析、存进 `MusicScoreInfo.timeSignature`，但**不参与任何位置或时间换算**；它只是记谱信息

之所以自动点可以脱离拍号：旧公式 `divisions = round(拍号 × 2)` 下，点间距恒为 `拍号 × 480 / (拍号 × 2) = 240` tick，拍号被约掉了。直接写 240 与旧公式在任何拍号下都等价，同时少一处乘法。

## 后果

- 判定、时间换算、长条高度、流速积分全部只有一条代码路径
- 非 4/4 谱面在**记谱意义上**的小节线不会与小节对齐（视觉上按四拍分组），这是已知且接受的取舍
- 送进 `NoteSpeedRatio.Resolve` 的「进度」就是 `bar + barProgress`，它与 tick 线性对应，流速积分因此不受拍号影响
- 若将来确实要按拍号画小节线，应当**新增**一条仅供显示的换算，而不是改动这条时间网格

## 教训

把「时间」和「记谱」混在同一个字段里（`bar`）时，任何按拍号调整它的改动都会同时移动流速积分、长条几何和自动点位置。这类改动无法靠单个谱面验证，必须至少有：一首带流速变化的 4/4 谱、一首非 4/4 谱、一首两者兼有的谱。
