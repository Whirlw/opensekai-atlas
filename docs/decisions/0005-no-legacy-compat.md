# ADR-0005：全新重构，不为历史数据保留兼容

> 目的：明确「哪些必须稳定、哪些可以随时改」，避免每次改动都被「旧数据怎么办」拖住。
> 适用读者：开发者。
> 前置条件：读过 [这是什么](../getting-started/what-is-this.md)。
> 最后更新：2026-11-02

## 状态

已生效（2026-11-02）。用户明确要求：发布之前不需要兼容任何历史遗留问题。

## 背景

这个仓库是**全新重构**，不是给线上产品打补丁。重构过程中反复出现「旧的 XX 还要不要读」的讨论：
旧编辑器工程文件、旧曲库页布局、旧页面注册表、旧历史记录格式、旧依赖。

如果每条都做兼容，会得到一堆迁移代码与双写分支，而收益是零——因为这些数据没有真实用户。

## 决定

**以下都不需要迁移、不需要兼容、不需要灰度：**

- 旧谱面编辑器的数据（`MusicScoreMakerData` 及其存档）
- 旧曲库 UI 的布局与 prefab（`ScreenLayerCustomMusicScoreManager`）
- 旧的页面注册表、旧内置曲包、旧 `ScreenLayerData`
- 旧的历史记录格式（新增字段只是**自带**，读不读得到旧记录无关紧要）
- 旧的依赖与包（uPalette / SoftMask / UI Particle / MessagePack / NuGetForUnity 已整块删除）

**唯一需要保持稳定的两个对外契约：**

1. `.oskp` 曲包格式：`manifest.json` / `score.json` / 音频 / 封面的字段名与目录结构
2. AssetBundle 清单字段名：`AssetBundleInfo` 的 `version` / `bundles` 与 `AssetBundleElement` 的字段

原因：用户自己导入的曲包会长期存在，AB 清单与已构建的包体对应。

## 后果

- 改动可以直接用最干净的写法，不必写迁移代码、不必留兼容分支、不必新旧双写
- 验收标准是「当前构建跑得通、数据能读能写」，不是「旧数据能继续用」
- 出现「旧数据读不出来」时，结论是**预期行为**，不是 bug

## 示例

判断某个兼容代码该不该写：

```text
旧格式只影响我们自己的历史产物（编辑器工程 / 旧曲库页 / 旧注册表） → 不写
旧格式是用户产生的文件（.oskp 曲包）                              → 写
旧格式是已构建产物的一部分（AB 清单字段名）                        → 写
```

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 为旧历史记录写迁移脚本 | 旧记录没有真实用户，迁移只会增加分支 |
| 保留旧曲库页做「兼容模式」 | 已用 `LibraryScreen` 取代，保留等于维护两套 UI |
