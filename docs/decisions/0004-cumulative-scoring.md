# ADR-0004：计分改为累积摊分，满判严格等于 1,000,000

> 目的：说明旧计分为什么会「全连不满分」，以及为什么用累积摊分而不是四舍五入补偿。
> 适用读者：开发者（改判定/计分）。
> 前置条件：读过 [打歌运行时](../architecture/live-runtime.md)。
> 最后更新：2026-11-02

## 状态

已生效（2026-11-02），口径版本 `RulesVersion = 2`。

## 背景

旧实现把每音符基分写成整数除法：

```csharp
BaseNoteScore = totalCombo > 0 ? Mathf.Max(1, 1_000_000 / totalCombo) : 0;
```

`int` 截断导致满判总分低于 1,000,000，缺口随音符数变化：

| 音符数 n | floor(1e6/n) | 满判总分 | 缺口 |
| --- | --- | --- | --- |
| 2019 | 495 | 999,405 | 595 |
| 348 | 2,873 | 999,804 | 196 |
| 64 | 15,625 | 1,000,000 | 0 |

真机自动打歌 2019 音符的曲子结算 `999,405`，一个音符都没漏 —— 用户可见的缺陷。

## 决定

第 i 个音符（0 基）的基分改为**累积差分**：

```text
base(i) = round(1e6 * (i+1) / n) - round(1e6 * i / n)
```

n 个音符全 JustPerfect 时前后项抵消，总分严格等于 1,000,000；单音符基分在相邻两值间跳动
（n=2019 时 495/496），误差不再堆到末尾。

实现：`ScoreLogic` 新增 `scoredNoteCount` 与 `TakeNextNoteBaseScore()`，`Setup()` 清零；
`BaseNoteScore` 字段保留供 UI/Technic 模式读取。

## 后果

**收益**：满判 = 1,000,000 成为可断言的验收条件；自动模式因此可以直接当「谱面/资源是否正常」的探针。

**代价**：手动打歌的分数与旧口径相差几分；历史记录里旧分数的口径不同。

**兼容处理**：`PlaySessionContext.RulesVersion` 1 → 2 标记口径；按 ADR-0005，旧分数不做迁移、不做换算。

## 验证

真机自动打歌 DEINOS PHAINEIN（Lv.35，2019 音符）修正后结算：`1,000,000 · S · 总音符 2019 · 自动判定 2019`。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 每个音符四舍五入 | 误差仍然存在，只是变小，满判仍不等于 1,000,000 |
| 最后一个音符补差 | 末音符分数会突然跳动，判定倍率也会异常 |
| 用浮点存总分、显示时取整 | 改变计分数据类型，影响面远大于修正 |
