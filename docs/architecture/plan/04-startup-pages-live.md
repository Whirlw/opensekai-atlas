## 6. 启动、页面与场景重构

### 6.1 新主场景

新增 `Library.unity`，作为首个构建场景。推荐保留现有 `Core.unity` 和 `TransitionBlank.unity`：

```text
Library ⇄ [需要时经过 TransitionBlank] ⇄ Core
```

第一轮不把全部内容塞进一个永久场景，也不同时引入新的叠加场景框架。保留已经可用的加载边界，降低生命周期改动。

从原编辑器入口接管以下必要动作：

- 确保唯一 EventSystem、字体和日志系统。
- 初始化本地设置、音量、资源与菜单音效。
- 按保存的设置应用帧率，避免每次返回曲库又覆盖为默认值。
- 创建 UI 层和曲库页面，处理进入／返回的遮罩。
- 明确应用切后台的音频与 Live 暂停行为。

初始化分成“应用一次”和“场景每次”两部分，避免与 Core 中的单例入口重复创建资源或重复注册事件。

### 6.2 页面收敛

| 页面 | 主要内容 | 导航规则 |
|---|---|---|
| 曲库 | 导入、歌曲列表、详情、手动／自动、设置 | 启动与退出 Live 的统一落点 |
| 设置 | 音量、流速、延迟、显示与帧率 | 关闭后返回原曲库状态，无编辑器恢复逻辑 |
| 加载 | 进度、错误、取消 | 每次仅允许一个开局请求 |
| Live HUD／暂停层 | 分数、连击、血量、判定、暂停 | 恢复／重开／退出，统一调用会话操作 |
| 结果 | 本局统计、模式标识、再玩一次、返回 | 不引用官方商业游戏的结果页骨架 |

推荐结果面板直接覆盖在 Core 的结束状态中，沿用 LiveOutUI 所需相机与 UI 容器，不新增一个重型结果场景。用户选择重开时重建局内状态，返回时卸载 Core。

曲库返回后恢复选中歌曲、滚动位置和筛选条件。保存的是轻量 UI 状态，不是整个编辑器 BootArg。

### 6.3 页面系统先收窄，再考虑替换

第一轮保留当前可用的 ScreenManager 子集，建立实际需要的页面注册表。现有 Header、加载、提示和弹窗可先复用。

新增或迁移页面时同步修改页面 ID、ScreenLayerData、注册表与 prefab 名称。不要直接复用原本没有 prefab 的页面枚举。

等闭环稳定后，若 ScreenManager 剩余依赖仍然过重，再缩成曲库／加载／Live 的小型导航器。**不把重写 4000 行页面框架设为移除编辑器的前置条件。**

### 6.4 清除返回编辑器的整条链

必须一并删除或替换：

- `OpenEditor`、编辑器返回设置、设置返回编辑器的代码和反射查找。
- `MusicScoreMakerEntryPoint.BootData`、`BootDataForSettingsReturn`。
- `IsTestPlay`、全连发布检查、试玩专属暂停与完成弹窗的执行分支。
- 撤销栈保存／恢复、发布完成标记等跨场景静态状态。
- `SoloLiveController` 与 `BaseLiveController` 中按编辑器首页判断返回行为的分支。
- `SceneManager.GetSceneName`、转场规则、`SceneTransitionBlank` 与 BuildSettings 中旧入口场景的映射。

需要暂存旧枚举值以兼容资源时，可保留数值占位；先断开执行入口，再在资源迁移完成后删除。不要重排可能被序列化的枚举值。

## 7. Live 会话轻量化

### 7.1 先收缩控制职责

第一阶段保留 `LiveLogic`、`ScoreLogic`、Note 家族与 `NotesViewManager`，把 `SoloLiveController` 收敛成会话协调器：

```text
Loading → Ready → Playing ⇄ Paused
                         ↓
                       Ending → Result → Disposed

加载错误／取消／退出 → 清理 → 曲库
Result／Paused → 重开 → 新一局 Ready
```

状态转换要求：

- Loading 时禁用重复开局；取消后，晚到的异步结果不得启动 Live。
- 暂停同步冻结判定时间、音乐、长按状态推进和相关表现。
- 倒数期间不推进判定时钟；恢复前清除过期触摸，核对长按续接语义。
- 重开清除所有判定、连击、生命、事件游标、输入缓存、完成回调和结果锁。
- 结束结果只生成一次，持久化只提交一次。
- 退出、异常和取消都释放本局拥有的资源，并恢复帧率策略、休眠与音量等全局状态。

`Completed`、`Retired`、`Failed`、`LoadError` 是不同的结束原因。当前生命归零后的行为需先记录基线，第一版默认保留；如果允许继续打到结束，结果应为 LifeZero，不能标记为普通 Clear。

### 7.2 启动数据只在适配器里组装

提取首页 `CreateDirectPlayBootData`，复用现有可运行字段填充。过渡期仍可生成 MasterMusic／Difficulty 等兼容对象，但 UI 不再认识这些类型。

后续按实际引用逐步移除无用 Deck、Model、Collaboration、Tournament、商业活动数据；不先重写整个 BootData 继承体系。

启动前验证的是转换后的谱面与资源，而不只是“NoteList 有一个非空元素”。断链、循环连接、无效 BPM／数值、缺少音频必须给出明确错误。纯装饰／Guide 的零计分谱面要显式定义行为：建议可用于自动观赏，手动模式提示无可计分音符，避免除零或错误 FC／AP。

### 7.3 结果与成绩

当前普通游玩主要是播放结算演出后退出；LiveOutUIController 的相关弹窗不能当作已经存在的完整成绩页面。新增轻量结果面板，展示：

- 歌曲与难度、手动／自动模式。
- 分数、最大连击、现有判定统计与 FC／AP／Clear／LifeZero 状态。
- 再玩一次、返回曲库。

先保留当前判定与计分系数，自动“模拟 Perfect”只影响展示，不混入手动最佳成绩。结果 UI、历史文件与最佳成绩都消费同一份 `PlayResult`。

继续读取 `PlayHistory.jsonl`，新记录可增加谱面内容哈希、规则版本和局 ID。旧记录缺少这些字段时作为旧版历史展示，不伪造哈希，也不直接与已替换谱面下的新成绩竞争最佳。第一版不因记录模型变化重写整份旧历史。

### 7.4 热路径先解决已发现的问题

代码中已确认 `LiveLogic.OnInput()` 每帧执行 `NativeInput.ActiveTouches.ToArray()`。将其改为对本帧稳定输入视图的遍历，或使用可复用缓冲；核对遍历期间集合是否可能变化。

后续按 Profiler 结果处理：

1. 每帧输入数组、LINQ、装箱、闭包、字符串与容器扩容。
2. 音符激活／回收窗口和对象池预热；保留负流速／单键变速下的双向可见区间语义。
3. 池中粒子、长条线与判定特效的重复实例化。
4. 每帧 HUD 全量刷新、布局重建和重复设置材质。
5. 固定宽高的高成本背景、RT 与视频纹理的过度驻留。

保留音符位置基于时间求值的做法，不改成 `deltaTime` 累加位移。首轮不迁移 ECS、Jobs、GPU 全谱渲染或自建复杂资源框架。

### 7.5 GC 与资源所有权

当前真机 LiveStart 会全局禁用 GC。重构时先记录分配来源，再评估恢复增量回收；不能在仍持续分配的情况下，仅关闭 GC 来掩盖问题。

资源所有权建议：

| 所有者 | 持有内容 | 释放时机 |
|---|---|---|
| 应用 | 公共字体、必要 UI、菜单音效、资源服务 | 应用关闭 |
| 曲库 | 可视项封面、曲包索引、预览音频 | 列表回收／离开曲库／缓存淘汰 |
| 会话 | 当前歌曲音频、运行时谱面、局内视图、RT、输入状态 | 结果退出／取消／异常；重开时受控复用静态资源 |
| 可选视频背景 | VideoPlayer、视频纹理与相关材质 | 背景关闭／本局释放 |

为外部 AudioClip 注册补齐成对的注销与释放，不仅清空 `CustomMusicScoreEntry` 的引用。异步请求、事件、协程与计时器同样需要清理。结果写盘前先取得值快照，不能在卸载后再读取已释放的局内对象。

## 8. 时间、输入与手感的处理策略

### 8.1 先统一时间命名与边界

明确三个概念：音频播放位置、减去 `fillerSec` 后的谱面时间、叠加用户判定偏移后的时间。存档单位、UI 单位、接口单位需要明确，不因变量名带 `Ms` 就假定其实际是毫秒。

加载音频、开始播放、暂停、恢复、重开都记录同一套时间锚点；`fillerSec` 和用户偏移各自只在规定边界应用一次。

### 8.2 输入回推修复单独实施

现有触摸与鼠标路径存在：

```csharp
musicTime = currentFrameInfo.time
          + (time - currentGameTime) * (1f / 60f);
```

两个时间值按当前实现以秒表达，额外乘 `1/60` 会压缩亚帧偏移。修复的候选表达是：

```text
输入对应谱面时间 = 当前谱面时间 + 映射到同一时钟域后的输入时间差
```

但实施前必须实测 Input System 时间与 `realtimeSinceStartupAsDouble` 的时钟原点、暂停和恢复偏移，建立显式映射，不能仅根据单位相同就直接相减。鼠标回落路径与触摸路径同步处理。

判定窗口第一轮仍按现有 `frame / 60` 对应的固定物理时长工作。120／240 FPS 不应使窗口随帧率缩放；提高输入时间精度也不需要同时放宽 JustPerfect 窗口。

### 8.3 不立即替换音频后端

`CriAtomShim` 当前使用 Stopwatch，并留有针对部分 Android 设备时间读数分块的注释。故不在删除编辑器时直接改成纯 DSP 时钟。

先定义 `IAudioClock` 或同等的窄接口，默认包住现有实现，收集实际音轨位置与时钟误差。若后续对比后端，再分别验证 Windows、Android 的长曲漂移、暂停恢复、播放启动和设备变化；通过后才改变默认实现。

首轮保留 SoundManager、Shim 和 ACB/HCA 解码链，因为菜单／打击音效还可能使用它们。官方 CRI 运行时是否可以移除，必须在排除组件、原生插件和资源引用后验证构建。不要同时进行音效转码与音频系统重写。
