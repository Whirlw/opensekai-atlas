# 基本原则

> 目的：定下写代码时的四条取舍标准，后面所有细则都是从这四条推出来的。
> 适用读者：所有人，尤其是要写新模块的人。
> 前置条件：读过 [README.md](README.md)。
> 最后更新：2026-11-02

## 概述

四条原则来自 Unity 官方风格指南，按"越靠前越优先"排列。它们回答的是同一个问题：**在没写细则的地方，怎么选？**

## 1.1 KISS：简洁优先

> Keep it simple, stupid.

优先采用简洁易懂的解决方案：

- **避免生僻语法**增加理解成本。C# 能写出很"炫"的一行（嵌套三元、LINQ 长链），但读的人要拆解半天，不如多写两行。
- **减少"重复造轮子"**，优先复用成熟工具或代码片段。

判断标准：一个新同事读完这段代码，能不能在 30 秒内说出它在干什么。

## 1.2 YAGNI：按需设计

> You aren't gonna need it.

基于当前**明确需求**设计方案，减少提前设计和过度设计。

原文的补充说明值得注意：并不是完全不能预留。开发者需要学习分析产品需求，**简单预测**后续可能新增的功能，可以保留**部分**对于目前存在冗余的设计。区别在于"预测"要有依据，而不是"万一会用上"。

反例：为一个只有一个实现的功能先写 `IStrategy` + `StrategyFactory` + 配置表。

## 1.3 渐进式开发：拥抱迭代

代码不是"一劳永逸"的。设计时**预留合理扩展性**，允许后续根据需求迭代优化，而不是追求"一次性完美"。

和 YAGNI 的关系：YAGNI 管"不要多写"，这条管"不要写死"。两者合起来就是——**接口留口子，实现别铺摊子**。

## 1.4 统一样式：一致性优先

团队内部维持代码样式统一，**比纠结"是否为行业主流样式"更重要**。

统一的样式带来的收益是具体的：

- 降低协作成本——不用先读一遍别人的风格再改；
- 提升可读性——同一类东西在同一位置、同一写法；
- 提升维护效率——格式化、重构工具能批量处理。

这也是本目录存在的理由：把"我们统一成这样"写下来，而不是每次靠记忆和感觉。

## 在本项目怎么用

| 场景 | 按哪条 |
| --- | --- |
| 想抽个接口/基类"以后可能有用" | 1.2 YAGNI，先不抽 |
| 需求变了要改结构 | 1.3，改，别怕；但先把边界留好 |
| 纠结 `_field` 还是 `m_field` | 1.4，按 [03-naming.md](03-naming.md) 来，别开新风格 |
| 一段逻辑写得聪明但难读 | 1.1，拆开写 |
