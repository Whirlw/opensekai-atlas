# 常见代码陷阱（Code Smell）

> 目的：把 Review 时最常说的五句话，变成一张可对照的清单。
> 适用读者：写代码的人和 Review 代码的人。
> 前置条件：无。
> 最后更新：2026-11-02

## 概述

代码气味是项目潜在隐患的信号。它不是"bug"，而是"将来会变成 bug"的结构。原文列出五条，下面逐条给出**症状 → 为什么坏 → 怎么改**。

## 五条清单

### 1. 命名模糊

**症状**：`int a`、`void DoThing()`、`var data`、`temp`、`flag`。

**为什么坏**：读代码的人必须跳到定义、顺着用法猜含义；搜索也无从下手（`a` 到处都是）。

**怎么改**：按 [03 篇](03-naming.md) 重命名。名字里带上"是什么 + 单位/范围"（`remainingHealth`、`elapsedSeconds`）。

### 2. 职责混乱

**症状**：一个类同时处理数据存储、业务逻辑和 UI 更新。

**为什么坏**："牵一发而动全身"——改 UI 可能弄坏存档，改存档可能弄坏判定。也没法单独测试。

**怎么改**：按 [07 篇 5.1](07-design-practices.md) 拆成"数据 / 流程 / 表现"三层。

### 3. 耦合过高

**症状**：修改一个类时，必须同步修改多个关联类。

**为什么坏**：扩展性差，改动成本随类数量指数上升；也无法替换其中一部分。

**怎么改**：先找"为什么必须同步改"——通常是直接 `new` 了具体类、或者互相持有引用。引入接口/事件解耦（事件写法见 [04 篇](04-events.md)）。

### 4. 重复代码

**症状**：相同逻辑反复编写，未提取为公共方法。

**为什么坏**：改一处漏一处，是最典型的线上事故来源。

**怎么改**：按 [07 篇 5.2](07-design-practices.md)，重复满 3 次提取。

### 5. 过度注释

**症状**：每行代码都加注释，或注释与代码重复（如 `// 声明变量a`）。

**为什么坏**：注释也会过期，过期注释比没有注释更危险；大量噪音会淹没真正重要的说明。

**怎么改**：按 [07 篇 5.3](07-design-practices.md)，只注释公共 API 的契约；Inspector 字段用 `[Tooltip]`。

## Review 时怎么用

按顺序扫一遍，命中就提：

```text
1. 名字能不能读出含义？            → 命名模糊
2. 这个类能不能一句话说清职责？    → 职责混乱
3. 改这里要不要同时改别处？        → 耦合过高
4. 这段逻辑在本文件/本目录出现过吗？ → 重复代码
5. 注释是不是在重复代码本身？      → 过度注释
```
