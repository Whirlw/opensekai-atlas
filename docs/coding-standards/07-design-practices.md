# 设计实践：职责、复用、注释、UI 命名

> 目的：把"能跑"的代码变成"好改"的代码，四条最常用的实践。
> 适用读者：写业务逻辑、维护模块的人。
> 前置条件：写过至少一个完整功能。
> 最后更新：2026-11-02

## 概述

这一篇从"格式"转向"结构"。前四篇管的是**长得像不像**，这篇管的是**拆得对不对**。

## 5.1 单一职责：一个类只干一件事

**一个类或一个类文件仅负责一个核心职责，复杂需求通过多个类的协作实现。**

原文举的例子：

- 数据存储类仅处理数据读写；
- 业务逻辑类仅处理流程控制；
- UI 类仅处理显示更新。

要避免的是"万能类"——那种几百行、什么都能干、改一行要通读全文的类。它的代价是：**改一个需求要理解全部**，测试也无从下手。

判断方法（整理者补充）：在类名上能一句话说清"它负责什么"，且这句话里没有"和"。说不清，通常就该拆。

本项目的分层可以对照着看：[模块划分](../architecture/modules.md) 里已经按 `App` / `Live` / `Infrastructure` 分了方向，新代码往对应层放，不要往一个 god class 里堆。

## 5.2 DRY：重复三次再提取

> Don't repeat yourself.

**当相同逻辑或流程出现 3 次及以上时，尝试提取为独立方法或工具类。**

为什么是"3 次"而不是"2 次"：

- 两次重复时，你还不知道它们的"相同"是不是巧合；
- 第三次出现，模式才稳定，提取出来才不会很快又被改回两份。

这条和 [YAGNI](01-principles.md) 是一对：**别提前抽象（YAGNI），也别放任复制（DRY）**，3 次是分界线。

## 5.3 注释规范

三条：

| 原则 | 做法 |
| --- | --- |
| 核心原则 | **不依赖注释解释混乱的代码**，优先通过优化命名和逻辑实现"自解释" |
| 注释范围 | 理想情况下**只对公共 API**（类、公共方法、接口）添加注释 |
| Unity 专属 | Inspector 面板可见的字段，用 `[Tooltip("描述")]` **替代**代码注释 |

原文还提到：Odin Toolkits 的 `[Summary]` 特性灵感来源于此——即把"给 Inspector 看的说明"从代码注释里搬出来，变成可渲染的元数据。

反过来的说法也成立：

```csharp
// 坏：注释在解释烂名字
// 把玩家血量减掉伤害值
int a = b - c;

// 好：名字自解释，注释只说契约
int remainingHealth = currentHealth - damage;
```

## 5.4 UI Toolkit 命名：BEM

UI 组件命名采用 BEM 规范，结构为：

```text
块（Block）__元素（Element）--修饰符（Modifier）
```

| 部分 | 含义 | 示例 |
| --- | --- | --- |
| 块 | 整体组件名称 | `navbar-menu`（导航菜单） |
| 元素 | 块内的子组件 | `shop-button`（商店按钮） |
| 修饰符 | 组件的状态或样式变体 | `--small`（小尺寸） |

完整示例：`navbar-menu__shop-button--small`（导航菜单中的小尺寸商店按钮），一眼能看出组件层级和属性。

### 用在 Unity 的哪里

- **UI Toolkit**：`.uxml` 里的 `class` 属性、`.uss` 里的选择器，直接照 BEM 写。
- **UGUI 的 GameObject 命名**：不需要 `__` / `--` 这么重，但"层级 + 变体"的思路可以借用，比如 `Panel__Shop--Compact`。
- **USS 选择器**：BEM 让选择器保持单层（`.navbar-menu__shop-button`），避免 `.a .b .c` 这种深层嵌套——UI Toolkit 的样式匹配是逐元素的，选择器越深越难覆盖。

参考：[CSS 命名规范整理](references/css-naming-conventions.md)。
